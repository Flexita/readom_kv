# 设备端安装器

使用者只往 Kindle 的 `documents` 里拷一个文件 `Readom.sh`。之后在 Kindle 书库点 "Readom"，安装、升级、修复、启动都在设备上完成。下载源是入口里烧进去的一张**有序地址表**（上限四条），按顺序试；哪个源取不到或者慢到下不完，就换下一个（`docs/design/release-build.md`「下载线路」）。

本文写给要改安装器和启动入口的人：现在的设计是什么、为什么这样设计、依据是什么。使用者看的安装步骤在 `docs/install.md`。

## 组成

| 部分 | 位置 | 作用 |
|---|---|---|
| 入口 | `boot/build_entry.py`、`boot/build_launcher.py`、`boot/launcher/` | 把交接模块、内核、公开初始化内存盘、安装器和画面打进一个 `Readom.sh`；点一次，先安装，再启动 Android |
| 发行载荷 | `installer/build_payload.py` | 系统镜像和空数据镜像的 zstd 包，以及记录大小和 SHA256 的清单 |
| 解包 | `installer/unpack/` | 核对载荷后展开成镜像文件 |
| 状态机 | `installer/install/` | 确认用户区里有本版本的系统镜像和可用的数据镜像，缺什么补什么 |
| 安装画面 | `installer/screens/render_screens.py`、`installer/install/screen.c` | 中英同屏的提示：构建时排版成位图，设备上拼成 PNG 交给原厂 `eips -g` |
| 日志与诊断 | `boot/launcher/userlog.c` | 每次点击一个日志目录，只留最近 5 次；内核日志按允许清单过滤 |
| 升级后应用重编 | `patches/aosp-frameworks-base/` 的 `0026`、`0047`、`0051` | 换了启动镜像后，由 Android 在首次开机时重编 `/data` 里的应用，不依赖构建机 |
| 上机检查 | `installer/probe/` | 量出安装器能依赖原厂系统的哪些能力 |

- **入口不含任何设备数据**：屏幕波形、Wi‑Fi 校准、ATAGs、存储布局、数据镜像 UUID，都在每次启动时从原厂系统现场生成（`boot/devicedata/`）。2026-10-15 在 PW3 上实测：现场生成的文件与此前私有入口里的逐字节相同。
- **入口只有一种，就是装发行版的那一种**。它不带测试脚手架：没有测试专用的 init rc、常驻的 logcat 采集、诊断开关、"放行框架启动"的闸门或保持唤醒的开关。没人看着的设备，不该带只有被看着时才用得上的东西。内核命令行在原厂那一段之后，只追加 `loglevel=1`、`panic=5`、`rdinit=` 和 `androidboot.hardware`、`androidboot.init_rc` 两个键（`build_entry.py` 的 `CMDLINE_ANDROID`）。
- **存储入口**：每次启动先比对系统镜像的记录（大小、修改时间、在 FAT 上的每一段位置）；对得上就不再通读，镜像变了才通读一次核对 SHA256（`device/amazon/pw3/preinit/SystemStamp.h`）。

## 发行载荷

`installer/build_payload.py` 在构建机里生成。**2026-11-03 建了新的候选版**（`/system` 改成 512 MiB，`/data` 仍是 1.75 GiB，数据格式仍是 1，所以现有设备原地升级）：入口 `Readom.sh` 7,759,418 字节 `acfc1a3a…`，载荷 190,830,823 字节 `6ca56d38…`、解出 536,870,912 字节 `b3213388…`，产物在构建机的 `build-share/entry-rc-v010-20261103/`、`payload-v010-20261103/`。**线上两个源上的附件还是 10-31 那一份**，所以这一版现在只能用离线包装；重传之后下面这张表和第 10b 步的数字要一起换。下面的数字取自**现在发出去的那一版**（载荷 2026-10-31 建，`build-share/payload-v010-20261031/`；入口 2026-11-01 建，`entry-v010-20261101/`）。权威值在官网那边的 `releases/v0.1.0.json`，数字过期了以它为准：

| 文件 | 大小 | 展开后 | 去向 |
|---|---|---|---|
| `readom-system-v0.1.0.img.zst` | 190.8 MB | 536.9 MB（512 MiB，2026-11-03 起；之前是 576 MiB） | 不在入口里；安装器按地址表逐个源下载，或从 `documents` 里取 |
| `readom-data-v0.1.0.img.zst` | 61 KB | 1.88 GB（1.75 GiB） | 放进 `Readom.sh`，不单独发行 |

- 两个镜像都用 zstd 压缩（级别 19，窗口 8 MiB，正是 `pw3-unpack` 接受的上限），设备上只需要一种解码器和 8 MiB 解码内存。数据模板曾用 Android 稀疏镜像（4.9 MB）；改成 zstd 压缩原始镜像后，小到能直接放进 `Readom.sh`，使用者少下载一个文件，稀疏镜像的代码也删掉了。
- **数据模板由 `build_payload.py` 自己造，源目录是空的**。AOSP 的 `userdata.img` 不是空镜像：`make userdataimage` 把 `$OUT/data` 里有什么就装什么，而那正是构建装测试模块的地方。开发期间发出过的一份模板里就带着 4.2 MB AOSP 原生测试程序；按同样办法再做，还会多出 `/data/app/PW3FormatTest.apk`，包管理器在使用者的设备上会扫到它。现在用 `make_ext4fs` 对空目录造，成品只有 `lost+found`；脚本再按超级块核对"11 个 inode、整镜像大小"，不对就拒绝。
- 清单（`manifest.json`，schema 4）记录每个文件压缩前后的大小和 SHA256，还记录构建时间（`built`，取自导出回执的 `built_utc`）、数据格式（`data_format`，现为 1：Android 8.1、1.75 GiB，见 `device/amazon/pw3/BoardConfig.mk`）和启动镜像哈希（`boot_image_sha256`，决定升级后要不要提示重编，见"只在换了启动镜像时提示重编译"）。
- 核对方法：在构建机上用 `pw3-unpack`（QEMU 下运行 ARM 版）展开两个文件，展开后的 SHA256 应与清单相同（`installer/unpack/test_unpack.py --payload`）。

## 安装流程

### 发行文件

| 文件 | 内容 | 大小 |
|---|---|---|
| `Readom.sh` | 入口脚本 + 静态辅助程序（安装和启动）+ 空数据镜像模板 + 清单 + 证书 + 画面 | 7,828,380 字节（约 7.8 MB） |
| `readom-system-<版本>.img.zst` | 系统镜像（zstd） | 190,831,781 字节（约 191 MB）。**面向使用者的地方一律只写"约 191 MB"**——画面、两份安装说明、官网都是这么写的；精确字节数只出现在 `SHA256SUMS` 和发行记录里，因为它每重建一次就变 |

- **清单**：版本号、系统载荷的文件名、大小和 SHA256、展开后的大小和 SHA256、下载地址。
- **证书**：curl 从 Mozilla 证书库提取的整套根证书（`source-lock.json` 的 `installer_ca_bundle`，2026-09-25 版，121 张，189 KB，MPL-2.0），交给原厂 `curl --cacert`。
  - 不只放 GitHub 现在用的两张根证书：GitHub 换过 CA（DigiCert → Sectigo），整套证书每次发行时更新。
  - 2026-10-15 核对：`github.com`（Sectigo E46，经 USERTrust ECC）和跳转后的 `release-assets.githubusercontent.com`（Let's Encrypt YR1，经 ISRG Root X1）都只靠这套证书校验通过。
- **清单写在 `Readom.sh` 里**，不单独下载：信任来自使用者从 GitHub 拿到的这一个文件，载荷只核对 SHA256，不需要另外签名。

### 用户区布局

```
/mnt/us/android/
├── system.img          512 MiB
├── data.img            1.75 GiB
├── state               安装状态（见下；先写临时文件，fsync，再改名）
├── report.bin          报告区，64 KiB（Android 写，安装器和启动器读）
├── download/           下载中的 .part 和下载完的载荷
└── logs/<时间>-<进程号>/  每次点击的日志，只留最近 5 次
```

### `state` 文件

```
schema=1
system=ready v0.1.0 <展开后的 SHA256>   或 system=writing（写到一半，镜像不可用）
boot=<64 位十六进制>                    系统的 ART 启动镜像，与上一行同一次写入
data=ready 1                            或 data=writing（正在从模板生成）
compiling=1                             数据镜像里的应用可能还在按新启动镜像重编译
compiling_after=<设提示时种进区里的序号>  这条提示要等的那次启动必须比它更靠后（见下）
android=<处理过的那一份>                报告区的 Android 启动计数（只用于拒绝报告的去重）
```

- 没有某一行，表示那个镜像还没有。
- `android=` 这一行：这次点击读得到报告区就写，包括写 `android=0`；读不到报告区的那次点击不写它。没有这一行时（状态文件写于开始记报告之前，或上一次点击读不到报告区），报告区里的那份不能当成本侧见过的：下一次点击只把序号记下来，不从它得出任何结论。
- 规则只有一条：**已有的数据镜像不覆盖**。只有 `state` 明确写着 `data=writing`（即是安装器自己生成到一半的），才会重新生成。
  - 状态文件不提数据镜像、盘上却有 `data.img`：这是有状态文件之前做的镜像，或状态文件写到一半断了电，也可能状态文件整个没了。**它的格式无从知道**，所以按本版本的格式算，再由大小来判：大小对就保留（并把格式补写回状态文件），不对就报 E304，不动它。写成"按格式 1 处理"只在只有一种格式的时候成立。一旦发过第二种格式，那条写法就会把每一台装好之后丢了记录的设备挡在外面——而且挡在交接之前，它连 Android 都进不去，除非使用者删掉数据镜像。大小是这里唯一的证据，所以**两种格式不能是同一个大小**；真要出现，那种格式必须把自己写进镜像里（ext4 卷标是去处），这条推断分不出来。
  - `state` 说有数据镜像，文件却不在：使用者删了它（相当于重置 Android 数据），重新生成一个空的。
  - `state` 写着 `data=ready` 时，交给 Android 之前先确认状态文件和它所在的目录已经落盘（`install.c` 的 `hand_over()`）；确认不了就报 E402，不进 Android。否则这条记录若只在页缓存里，断电后下一次点击会读到 `data=writing`，拿空模板盖掉使用者用过的数据镜像。

### 每次点 Readom 的流程

每一步都可以重入。中途没电、强制重启，或书库在使用者离开时杀掉脚本后，再点一次就从断点继续。

1. **核对本机**：原厂 `eips` 的哈希、原厂内核版本串、设备数据能否提取。机型或固件不符就报 E101，不改动任何文件（`eips` 本身对不上时什么都画不了，直接退出）。
2. **加锁**：锁住 `android/` 目录（`flock`），直到进入 Android。
   - 原因：sh_integration 在使用者离开时只 `kill -9` 它启动的那个进程（[源码](https://github.com/KindleModding/sh_integration/blob/main/launcher/main.c)），安装器会作为孤儿继续运行。
   - 使用者再点一次时，第二份安装器拿不到锁，只提示"正在安装"（E103），不会和第一份写同一个文件。
   - sh_integration 本身不限制运行时长。
3. **查 USB**：Kindle 连着电脑就报 E104。每次点击都查，在安装和启动之前。
4. **读报告区和 `state`**：先读报告区里上一次 Android 启动留下的报告（见"从报告区读回来的两件事"）。然后，系统镜像的版本和 SHA256 与本入口相同、大小正确，数据镜像格式相同、大小正确，就直接启动：不查电量，镜像也不动。开机时存储入口还会核对系统镜像。
5. **否则安装**：
   1. 数据镜像格式不是本版本的：E304，什么都不改。这一步在写系统镜像之前，免得装上新系统却用不了旧数据。
   2. 电量不低于 40% 或正在充电，否则 E102。读不到电量时不拦。
   3. 空间：一次算出还差多少，不够就报 E401 并给出 MB 数。
      - 顺序固定为：下载 → 写系统镜像 → 删载荷 → 生成数据镜像。所以同时要占的空间是"载荷 + 系统镜像"和"系统镜像 + 数据镜像"中较大的那个，比三者之和少一个载荷（约 191 MB）。
      - 首次安装要的是系统镜像加数据镜像，512 MiB + 1.75 GiB，另外给原厂系统留 64 MiB，合计 2,483,027,968 字节（2.3125 GiB，2.49 GB；`docs/install.md` 对外写的是"至少 2.6 GB"，多出的约 117 MB 容得下 7.7 MB 的入口和日志）。
   4. 交叉链检查（`fatcheck.c`）：**这一次要覆盖、而且现在长度大于 0 的**那些镜像，按它们现在的长度问 FAT——每个簇是不是只属于这一个文件。保留下来的数据镜像不在范围内（这一次不写它）；两个都不在范围内就直接返回，什么也不问。只有确认共用才报 **E404**（见 `installer/install/fatcheck.h`）；问不出来（卷认不出、目录太深、段数超上限）只打一行日志、照常安装，因为"能不能看"和"看了没事"不是一回事，而这条防的故障需要一个本来就不一致的 FAT。干净安装时两个镜像都还不存在，没有簇可以和别人撞，这一步整个跳过。**报 E404 时没有往镜像里写过任何字节**。身份还没从真机采集的构建在写镜像之前停在 **E105**，同样不写系统镜像。——但这一次点击可能已经写过 `state`、建过报告区，所以屏幕上说的是"没有往那里写"，不是"什么都没做"。
   5. 系统载荷：先在 `documents/` 和 `android/download/` 里找同名、同大小的文件。
      - 找不到就下载：先查 Wi‑Fi 已连接（否则 E202）、本机时间不早于构建时间（允许差 24 小时；否则 TLS 无法校验，E203）。下载时证书校验失败（curl 返回 60，多半是时钟拨得太靠后）也报 E203。
      - 原厂 `curl` 只走 HTTPS（跳转后也是），配自带证书，`-C -` 续传到 `download/<名>.part`，下完改名。
      - **入口里是一个有序的地址表**（最多 4 个，`INST_MAX_ORIGINS`）。每次尝试问一个源，有字节进来就一直问它（每次换源都要重做一次 TLS）；一个字节都没来就换下一个，所以取不到的源只花一次尝试。某个源答 404／410／416 或长度不对，是**这个源没有这个文件**，换下一个；每个源都这么说才是 E303。换源时分片不丢——各源装的是同一个对象，而载荷是整份到齐后按 SHA-256 准入的，跨源拼出来的分片受同一道校验。
      - 一次传输 60 秒内低于 1 KB/s 就结束，再续传；两个额度都按源计：连续 2×源数 次没有进展、或一共试满 6×源数 次，报 E201。**只有一个源时和多源之前逐字等价。****六次是接力，不是六次重试同一件事**：`idle` 只在这一次一个字节都没多下来时才累加，有进展就归零，所以一次传了 180 MB 然后断掉算有进展。回源到 GitHub 那条线上这件事更要紧：附件的签名地址带着**约 30 分钟**的有效期（官网会话 2026-10-30 实测，看的是 URL 里的 `se=` 参数），而 Kindle 的 Wi-Fi 慢到 100 KB/s 时 190 MB 要三十多分钟。**已经开始的传输会不会在到期那一刻被掐断，没有实测过**——那次只取了 100 字节；S3 的文档说到期是在请求时判定、已开始的下载可以跨过到期点，但这不足以证明 GitHub 当前后端的行为。两种结果这边都接得住：真被掐断就是一次有进展的失败，下一次尝试重走 302 拿新签名、从断点接着下，所以**不需要为签名到期专门写代码**。R2 命中那条没有签名也没有第二跳。
      - 续传跨得过跨主机的 302：`readom.app 302 → github.com 302 → release-assets.githubusercontent.com 206`，两跳，在 `--max-redirs 5` 之内，全程 https（同一次实测）。**能续传的部分留着，不能续传的不留**：`curl` 报 33/36（服务器不接受续传）时删掉分片从头下，六次都这样就一个字节都没留下。所以 E201 不承诺盘上还有东西。
      - 服务器返回 404/410，或文件大小与清单不同：E303。续传请求落在对象末尾之外（HTTP 416）也是 E303：进下载循环时分片一定短于清单，所以 416 只能是服务器上的对象比清单短，那就不是清单描述的那个文件。这一条按 HTTP 应答判，不按 `curl` 退出码——`--continue-at` 遇上 416，有些版本的 `curl` 把它当成"你已经下完了"而返回 0，`--fail` 也不改变这一点。
   6. 展开系统镜像（`pw3-unpack`）：
      - 先核对载荷的 SHA256，核对通过之后、写第一个字节之前，才把 `state` 改成 `system=writing`。所以载荷损坏时旧系统仍然可用。
      - 写完写 `system=ready`，确认状态文件已落盘后再删掉载荷（`download/` 下的全部和 `documents/` 里本版本的同名文件）。展开时已逐字节核对 SHA256，不必为保留载荷多占约 191 MB。确认不了落盘就先留着，之后哪次点击发现系统已就位、状态已落盘，再清掉。
      - 结果码对应如下：

        | 结果码 | 含义 | 处理 |
        |---|---|---|
        | 1、2 | 载荷不完整或损坏 | 删除坏文件，报 E302 |
        | 3 | 发行缺陷 | 报 E303 |
        | 4 | 空间不够 | 报 E401 |
        | 5 | 读写出错 | 报 E402 |
        | 6 | 内存不够 | 报 E403 |
        | 7 | 写第一个字节之前没能把状态记下来 | 报 E402 |

   7. 数据镜像：没有就先写 `data=writing`，再从内置模板展开，写完写 `data=ready 1`。
6. **启动**：走启动流程。90 秒的启动时限在安装期间暂停，从这里重新开始算。

安装期间阻止原厂进入屏保（`lipc-set-prop com.lab126.powerd preventScreenSaver 1`），结束后恢复原值。屏幕提示见"安装画面"。

**下载时开 Wi‑Fi 不会让原厂固件被升级**：亚马逊已不再给 PW3 发固件；越狱后 jb.sh 会停用并改名 OTA 守护进程。支持其他机型时，要在各自的机型档案里重新确认。

### 错误码（屏幕上同时显示中英文说明）

停在错误屏的那一次点击不会马上退出：越狱带的 sh_integration 启动器在脚本退出约 1.2 秒后把整屏重画成书库（2026-11-04 屏幕探针实测，启动器 v4.1.0），所以入口独占触屏（`EVIOCGRAB`，只在没有手指时取、放），画完收尾的那一屏后等使用者点一下再退出。触屏从这次运行画第一屏起就独占（`kindle_take_touch`；那一刻有手指就等下一次画屏再取，内核拒绝独占就不再试）：2026-11-05 装机时使用者在 0% 处从顶部下滑看 Wi‑Fi，原厂下拉菜单盖住进度、关上后留下白屏；安装进度同一屏 30 秒没重画也会整屏重画一次（`show`，`REPAINT_MS`；错误屏不重画，停住时由独占触屏挡住原厂菜单）。等点击时先问驱动有没有手指、再把队列读空：那一刻已经结束的触摸，按下那一帧必定已在队列里被读走（驱动先结束带按下的那一帧，才在后面的帧里报抬起），正按着的那一下放完不算（读空时恰好抬起的，再问一次、再读空一次），之后读到的按下都是新的。不看事件时间戳，因为那是墙上时间，Kindle 校时会让它跳。「睡过」按开机时间减单调时间判断，开机时间读 `/proc/uptime`，不读 `CLOCK_BOOTTIME`：原厂内核带着补丁 0103 修的那个溢出，Kindle 睡过之后每秒里有一段时间读数少 4.29 秒；入口 p 及以前用的是后者，会偶尔把错误屏误判成「睡过」而提前放掉（2026-11-05 Codex 复审对着原厂源码查出）；最长 10 分钟，Kindle 睡过、收到停止请求、或运行它的脚本没了也结束（`kindle.c`，`kindle_hold_screen`）。每张错误屏末句是「看完点一下屏幕，回到书库」；入口自己没能画屏、只剩兜底一行字时同样停住。已知残留：独占和查状态之间恰好落下的手指会被拆开（原厂 evdev 没有原子的取并查）；只发给外层 shell 的 TERM 在它等前台 helper 时传不到 helper。

## 解包工具 `unpack/`

`pw3_unpack()`：先核对载荷的大小和 SHA-256，不对就不写任何东西；再把 zstd 展开成镜像文件，边写边算输出的 SHA-256。安装器直接链接它，`pw3-unpack` 命令行版供测试和手工使用。只链接 zstd 1.5.6 的解压部分（`source-lock.json` 的 `installer_zstd`，BSD-3-Clause 或 GPL-2.0-only，发行时要随附许可）。

- **怎么写**：
  - 原地覆盖已有的镜像，最后截到清单大小，所以升级时不需要两份空间。没写完之前镜像不可用，重跑就从头开始。
  - 每写 8 MiB 推到设备上，并清出页缓存：原厂系统空闲内存只有约 10 MB，进度显示的是已落盘的量。
  - zstd 窗口限制在 8 MiB；需要更大窗口的帧直接拒绝，不分配内存。
  - `before_write` 回调：核对通过、确认空间之后，写第一个字节之前调用。安装器在这里把 `state` 改成"写到一半"。
- **结果码**：`unpack.h`。1 文件不完整，2 文件损坏，3 载荷本身有缺陷，4 空间不够（同时给出还差多少字节），5 读写出错，6 内存不够，7 被 `before_write` 中止。
- **帧结束恰好落在输出缓冲写满时**：展开后的大小正好是 1 MiB 输出缓冲的整数倍、且帧恰好在缓冲写满时结束，这时循环不能再调一次解码器——解码器已开始等下一帧，会返回非零，被误判为"流在帧中间结束"。真实的 1.75 GiB 数据镜像和 512 MiB 系统镜像都是 1 MiB 的整数倍，所以这条边界真实存在；测试里有专门触发它的一项。
- **测试**：`unpack/test_unpack.py`，QEMU 下运行 ARM 版。
  - zstd：多帧、可跳过帧、帧结束在缓冲边界、窗口超限、截断、损坏、清单大小不符、空间不足。
  - 给出一份发行载荷时，两个文件都展开并计时。开发期间实测：604 MB 系统镜像 25 秒、1.88 GB 数据镜像 22 秒，展开后的 SHA-256 都与清单相同。

测试覆盖：

- 安装：从 `documents/` 安装、再点一次（不查电量、不写）、升级保留数据。
- 升级时载荷损坏：旧系统仍可用，坏文件删除。
- 数据格式不符：E304，什么都不改。
- 前置检查：电量低（E102；充电或读不到电量时照常安装）、离线（E202）、时钟早于发行（E203）、空间不足（E401，给出差额）。

### 接入入口

- `boot/build_entry.py` 接受 `--installer`（`build_payload.py` 的输出）、`--screens`（`render_screens.py` 的输出）、`--release-url`、`--ca-bundle`、`--zstd-archive` 五个参数，必须一起给；它再把这些连同导出的 `system.raw.img`（`--system-image`）交给 `boot/build_launcher.py`。
  - 带上它们，辅助程序以 `PW3_INSTALLER` 编译，在原厂系统检查之后、加载交接模块之前先运行安装器。
  - `build_launcher.py` 不带 `--installer` 时构建的是不含安装器的启动器，现在只有 QEMU 下的 `boot/handoff/tests/run_client_test.py` 这样用。
- 构建时核对：
  - 系统镜像路径必须是 `android/system.img`，大小和 SHA256 必须与载荷清单一致；
  - 数据镜像必须是 `android/data.img`，大小与模板展开后相同；
  - 证书库和 zstd 源码包必须与 `source-lock.json` 相同；
  - 画面必须是按同一个载荷、同一个机型档案渲染的。
- **下载地址**：`--release-url` 给的是资产所在的目录，形如 `https://github.com/OWNER/REPO/releases/download/TAG`；`build_launcher.py` 按这个形状核对，再拼上载荷文件名，不接受整个文件地址，也不接受 tag 页面。版本写错不需要单独检查：载荷按 SHA256 认，错的文件会被拒绝而不会装上。资产在不在，只能在上传之后实际取一次来确认（`docs/design/release-build.md`）。
- **出错时的退出码**：辅助程序只有在原因确实画到了屏幕上时才以 3 退出，入口脚本见到 3 就不再追加文字。其他非零退出码，入口脚本用 `eips` 打一行英文兜底：`ANDROID DID NOT START. FREE SOME SPACE ON THE KINDLE DRIVE AND TAP AGAIN.`（走到这一行，多半是用户区满得连本次的日志目录都建不了）。这一行下面再打一行 `TAP THE SCREEN TO GO BACK TO THE LIBRARY.`，由核过哈希的辅助程序（`--hold-screen`）停到点一下屏幕，盘满建不了日志目录时也先把它解进 /tmp；收到停止请求就不停。
- **大小**：现在这一版 `Readom.sh` 是 7,828,380 字节。其中安装器带进来的数据是空数据模板 61 KB、证书 189 KB、画面 681 KB，进脚本时再经 base64。

## 只在换了启动镜像时提示重编译

"已安装的应用要重新编译"这句话的前提，是新版本换了启动镜像。应用重编与否是 ART 按启动镜像决定的（odex 里记着它是对着哪个启动镜像编的；补丁 `0026` 逐个调 `getDexOptNeeded`，没变的直接跳过），与构建指纹、版本号都无关。本项目刻意保持 `/system/framework` 下 `arm` 子目录里那 45 个 `boot-*.art/oat/vdex` 逐字节不变，每次构建后都逐字节比对，所以**多数升级根本不重编**。如果每次升级都显示这一屏，使用者多数时候是在白等。因此 `BOOT_UPGRADE` 只在真的换了启动镜像时显示。

判断的依据一路带到安装器：

| 环节 | 做什么 |
|---|---|
| `export-aosp-images.py` | 回执里记 `boot_image`：用 debugfs 从**导出的那个镜像**里取出 `/system/framework` 下 `arm` 子目录的 `boot*`，按文件名排序，名字和内容一起进哈希（多一个或少一个文件都算变） |
| `build_payload.py` | 清单里记 `boot_image_sha256`（schema 4） |
| `build_launcher.py` | 写进 `pw3_release.boot_image`，并记进入口回执 |
| `build_launcher.py` | 还从**导出的那个镜像**（`--system-image`，先核对 SHA256 是载荷展开后的那一个）里用 debugfs 读 `build.prop`，把 `ro.build.version.incremental` 写进 `pw3_release.build_incremental`——完成报告靠它认身份。值必须是采样器会原样写出来的那种（可打印 ASCII、不超过 `Clean()` 的上限，上限也是从 `BootReport.cpp` 里读出来比的），否则构建就停在这里 |
| `install.c` | `state` 里写一行 `boot=<64 位十六进制>`，与 `system=ready` **同一次**写入；`upgraded = 装了新系统 && 保留了数据镜像 && 启动镜像变了`，在动手写任何东西之前就定好 |

三条取舍：

- **没有记录时按"变了"处理。** 警告多一次是看一眼就过去，少一次是让人干等还不知道为什么（`install.c` 里对 `compiling` 的清除也是同一条取舍：只按证据清，不设上限）。
- **不替没有记录的状态文件"补记"启动镜像。** 补记的依据是"状态文件说的系统就是盘上那个系统"，而这正是被质疑的那条记录——有人用 USB 换上一个同样大小的 `system.img`，安装器这边的每一项检查都过得去（`need_system` 比的是记录里的 SHA256，不是文件）。宁可下一次升级多提示一次。
- **启动镜像没变，不等于上一次欠的重编译已经做完。** 同一启动镜像的升级不新增重编译，但也不能把前一次没走完的提示清掉；`compiling=1` 保留，这一次启动照样提示。

**为什么要和系统记录同一次写入**：如果分两次写——先写"系统装好了"，再写那条提示，中间还隔着删那个约 191 MB 的载荷——在这个窗口断电，状态文件就只剩"装好了"。下次点进去显示的是普通的那一屏，它不提编译，而设备正在重编译。所以一次写完（写临时文件 → fsync → rename）。

## 从报告区读回来的两件事

原厂侧通过报告区（`docs/design/diagnostics.md`）知道上一次 Android 启动走到了哪一步。安装器据此做两个决定，而不是靠数点击次数去猜（`install.c` 的 `read_report`，每次点击读 64 KB）：

| 读到什么 | 做什么 |
|---|---|
| 不是拒绝报告、报告里最后一次采样到 `sys.boot_completed=1`、`ro.build.version.incremental=` 正是本入口所装的那个系统，**且序号比 `compiling_after=` 更靠后** | 这次启动走到了 `boot_completed`，而重编译发生在 `SystemServer.startOtherServices()` 里的 `updatePackagesIfNeeded()`（比同一函数里的 `systemReady()` 早 700 多行），所以编译必然做完了：清掉 `compiling=1` |
| 序号不同，且 `preinit_stopped=` 是系统镜像哈希不符或超级块不对 | Android 拒绝了盘上那个镜像。抹掉 `system=ready`、先显示 `REPAIR` 画面说明再重装。数据镜像不动，`boot=` 保留（同一个版本的镜像重写不带来新的重编译） |
| 序号不同，`preinit_stopped=` 是别的原因 | 重装解决不了，只记进日志；使用者手上有一句可看、可转交的话 |
| 没有报告、校验和不符、全零、首行不完整 | 什么都不做 |

几条边界：

- **处理过的报告不再处理。** 拒绝报告会一直留在区里，直到下一次 Android 启动盖掉它；`android=<序号>` 就是"本侧已经处理到哪一份"。没有它，使用者每次在两分钟内退出，都要白等一次 512 MiB 重写。
- **提示清不清，问的是"谁的启动"，不是"第几次启动"。** 报告正文里有一行 `ro.build.version.incremental=`，采样器第一轮就记它：报告到了读它的人手上时，已经和它来自的那次启动分开了，而其他每一行的含义都取决于这个答案。安装器把它和自己装的那个系统的同一个值（`build_incremental`）比。对上才算证据；对不上、没有这一行、或者报告根本不说，提示都留着。
  - 曾考虑用计数代替身份，即"见过的最大序号"，永不减小；没有采用。序号写在报告首行，而 CRC32 只盖正文，**一个比特翻转就能把水位抬到没有一份诚实报告能过去**；报告区被重建后计数从 1 重新开始，水位量的是重建之前那段序列。根因是同一句：**计数回答不了"这是谁干的活"**，而身份本来就在报告里。
  - **身份挡不住"同一个版本的更早一次启动"**：装过 A → 装 B（启动镜像不同）→ 再装回 A，这时 A 欠着编译，而把 A 当初那份完成报告拷回来，版本号是对的。所以设提示的那一刻定一个下限 `compiling_after=`，清提示要求"比它更靠后"。这个数**随提示生灭**，不是永久水位。
  - **这个下限是种进去的，不是读出来的。** 下一次启动写的序号必然是区里那个数加一，所以安装器在设提示的同时自己重写报告区，把数种进去（`pw3_report_build_made`）。种的是**时钟**（不低于本版构建时间、不高于 2^31）：要成立的事实是"这次安装之前写的报告序号一定更小"，而时钟是这台设备上唯一只会向前走的数。
    - 读区里的数当下限站不住，两条都可达：序号写在首行而 CRC 只盖正文，**一个比特翻转**就能把下限抬到 `0xffffffff`（写入方回绕到 1，于是没有任何诚实报告能越过它）；而计数一旦重启（任何一次区重建），同版本旧报告的序号反而**更大**。
    - 区写不进去时（存储满），下限退回"区里那个数"，并在日志里说明。这是降级的那条路。
  - 所以 `android=` 只回答拒绝报告的去重，**它可以往回走**（区读不出来时下一次写入从 1 重新开始，基线不退就会把同一份拒绝每次都当成新的）。读到的区是安装器自己写的那份占位报告时，这个数**要清掉**：它指的那份报告已经不在这个区里了，留着会让重建后的第一份拒绝（序号也是 1）被当成"处理过的"，白走一次"启动失败再回来"。
- **两个方向分开问。** 拒绝判"序号不同"，完成判"是不是本入口装的那个系统写的"。少判一次拒绝是永久死路，多判一次只是多重装一遍（屏幕上有说明）；晚清一次提示只是多看一眼，早清一次是让人在 dexopt 中途按电源键。两种错代价不对等，所以不共用一个判据。
- **首行坏了魔数的报告要清零重来。** 一个字节的翻转就能让报告通道永久死掉：安装器因为大小对而不碰它，preinit 因为"不是我们的"而不映射它。判据不是"状态文件说这是我做的"（那记的是路径，不是文件——换一个同样大小的陌生文件进去就会被清空），而是文件自己：把魔数补回去，首行解析得出来、正文 CRC32 对得上它声明的长度，就是我们那份坏掉了（`pw3_report_damaged_magic`）。读不过去不算坏——照"打不开"处理，原样留下。
- **序号不从日志文件夹推。** 启动器确实在 `android/logs/` 里留报告副本，但那些会轮转、会被人删、存储紧张时根本不写（设计上就是"顺手留下的"）。安装与否的决定不能靠按设计可丢弃的文件。

这些规则由 `installer/install/test_install.py` 和 `tools/run-tests.py` 的 `report-area` 一项覆盖。

## 诊断：日志目录就是诊断包

安装器不另设"Android 管理"入口。曾考虑在一个入口里做修复、导出诊断、卸载三件事；按使用者实际会遇到什么逐一看，只有导出诊断是真缺口，而它也不需要新入口。

### 为什么不做菜单

书库里的入口只能被"点一下"，没有键盘，安装器画面也不读触摸。要在一个入口里选三件事，就得自己从 `/dev/input/event*` 读触摸、画按钮、处理误触——为三个动作新增一整套输入和界面。先看这三件事各自是不是真的需要它：

| 功能 | 现在怎么办 | 要不要做成按钮 |
|---|---|---|
| **修复**（系统镜像损坏） | 不用使用者操作：Android 拒绝启动并把原因写进报告区，下一次点击读到后自动重装（见上节）。启动画面上写着"回到了书库就再点一次" | **不要**。已经不需要使用者做任何选择 |
| **卸载** | 删 `android` 文件夹和 `documents/Readom.sh`（`docs/install.md`） | **不要**。而且删除是不可逆的，没有输入就没法做二次确认，做成一点就执行的按钮反而更危险 |
| **导出诊断** | 日志目录本身就是诊断包（见下） | **不要**。出了问题，使用者手上只有一块不说话的墨水屏，这是真缺口；但补上它不需要按钮 |

每点一次 Readom，启动器本来就要往 `android/logs/<时间>-<进程号>/` 写这次的日志、哈希清单和失败证据，并保留最近 5 次。**把那个目录本身做成诊断包**，就什么都不用新增：

- 位置固定，使用者用电脑打开 Kindle 盘就看得见；
- 出问题的那次一定在里面（保留 5 次）；
- 不用多一个书库条目，不用多点一次，也不会有人在"该点哪个"上犯难。

### 目录里有什么

| 文件 | 内容 |
|---|---|
| `launcher.log` | 入口脚本和辅助程序的输出：本机核对、安装器每一步（`PW3_INSTALL …`，每次写 `state` 都把整份内容记成一行）、交接前的检查 |
| `previous-kernel.txt` | 上一次 Android 运行期间的内核日志，按允许清单筛过（见下） |
| `android-report.txt` | 报告区里上一次 Android 启动写的报告，逐行筛过 |
| `<阶段>-before-kernel.txt`、`<阶段>-after-kernel.txt` | 交接前休眠检查前后的内核日志，按允许清单筛过 |
| `preflight-complete.txt` 等 | 交接前检查的结果 |
| `launcher-complete.txt`、`SHA256SUMS` | 辅助程序的退出码；目录里每个文件的哈希 |

这些文件都是本项目写的，按设计不记录任何设备标识。

**内核日志只能用允许清单**。原厂内核日志里会出现 MAC 地址、Wi‑Fi 名称、序列号；"把认识的敏感词删掉"这种黑名单做法，漏掉一种写法就泄露一次，而能出现什么是列不完的。所以反过来：只留开头匹配本项目和几个已知子系统的行（`pw3-`、`mxc_epdc`、`mmc0`、`EXT4-fs`…），其余一律不要。宁可少给几行，也不把"没想到的那一行"带出去。

### 写在哪几屏上，为什么不打包

- **写在三屏上**：重装屏的"反复出现"那一段、E303、以及"没能启动"。判据是"这一屏之后该做的事是报告"——剩下的屏要么自己能解决（充电、连 Wi‑Fi、删书），要么本来就不是故障。
- **不打包**。目录就是诊断包：位置固定、出问题那次一定在里面、不用多点一次。`busybox tar` 能打，但使用者此刻正坐在电脑前，而每台电脑都会把文件夹压成一个包——多写一段代码去替他做一件他本来就会做的事，不值得。
- "没能启动"那一屏让使用者先再点一次，而不是先重启：原因在报告区里，下一次点击会读到它，该重装的会自己重装。

### Android 运行期间的情况怎么带回来

Android 的日志和开机时间线都在 `data.img` 里，原厂系统读不了那个 ext4 镜像（原厂内核没有 ext4），也不该读。有两条路把 Android 那一侧的情况带回原厂侧：

- **内核日志不走文件。** 两边内核都带 lab126 的 `CONFIG_LAB126_PRINTK_BUFFER`，命令行里都有 `log_pos_goal=0x8fff0000`，于是 Android 运行期间的内核日志留在固定物理地址，重启回原厂后由原厂内核以 `/proc/printkbuf` 发布出来（形态是环形缓冲区的原始内存，不按时间顺序）。入口每次点击都把它按同一套允许清单筛过，存成 `previous-kernel.txt`。驱动报错、OOM、面板、存储、USB、内核崩溃都在里面。
- **用户态靠报告区。** Android 启动时把采样结果写进报告区，启动器下一次点击把它逐行筛过，存成 `android-report.txt`。报告不抄 logcat 原文，只记各组件告警和错误的条数（`android_error_count 标签=条数`，`device/amazon/pw3/initcheck/BootReport.cpp` 的 `Errors()`）：应用写进日志的东西（包名、路径、网址、打开的文件）是使用者的，而这个文件是要附进问题报告、会公开的。

logcat 和 tombstone 的原文仍然只在 `data.img` 里。

### 日志目录与内核日志过滤

两件事都在 `boot/launcher/userlog.c` 里。它独立于启动那条路径，所以能在本机测（`tools/run-tests.py` 的 `user-log`）。

- 发行入口每次点击写 `/mnt/us/android/logs/<时间>-<进程号>/`，连本次共留 5 个，其余删掉；内核日志按允许清单过滤。
- 不带 `--installer` 构建的启动器（只给 QEMU 下的 `run_client_test.py` 用）写到用户区顶层的 `/mnt/us/pw3-first-kernel-<时间>-<进程号>/`，不删、不过滤：在别人的盘顶层按前缀删东西，不是本项目该做的事。

前缀只写在两处：入口脚本里的 `@LOGPREFIX@`（`build_launcher.py` 填入）和 `helper.c` 里的 `PW3_OUTPUT_PREFIX`，两者都按是否带安装器选。脚本先 `mkdir -p` 上一级再建本次目录；脚本和辅助程序对后缀都只接受 `[0-9TZ-]`、2–80 个字符。

**轮转怎么删**（`pw3_logs_rotate`）：只在 `android/logs` 这一层里挑候选，名字必须正好是启动器自己的形状（15 位时间戳 `YYYYMMDDTHHMMSS`、`-`、进程号，17–80 个字符），必须是目录（`AT_SYMLINK_NOFOLLOW`），里面必须全是普通文件——有子目录、有符号链接、有任何别的东西就整个放过。然后 `unlinkat` 逐个删文件、`unlinkat(AT_REMOVEDIR)` 删目录；不按前缀匹配、不跟随链接、不递归，本次的目录按名字排除。删不掉不算错误：这是家务，不能成为开不了机的理由。

**正在写的目录不删**。目录名是时间，时钟往回走时，后启动的那次反而名字更小，所以"哪个目录还有人在写"不能按名字判断，只能问内核：

- 每次点击打开自己的目录后，立刻对它加一把共享锁（`pw3_logs_hold`）。锁随进程存在，进程被 OOM 杀掉时内核自动收回，残留的目录照常被回收。
- 轮转放在安装锁之内，同一时刻只有一次点击在轮转。删一个目录之前先对它要排他锁（`LOCK_EX | LOCK_NB`），只有拿到才删；任何失败都把目录留给下一次点击。锁要一直持有到 `rmdir` 之后（`rmdir` 不看建议锁），所以删除方另 `dup` 一个描述符拿着它。
- 拿到安装锁之后，辅助程序再核对一次自己的目录是不是还在、名字是不是还指向它；不在就停下。

**内核日志为什么是允许清单，以及实测**：原始日志里有 `usb0: MAC …` 这样带设备 MAC 的行，这就是黑名单不可取的原因：能出现什么是列不完的。允许清单按"本项目用到的子系统 + 内核出事的形状"写（`userlog.c` 的 `ALLOW`）：

- 休眠路径：`PM:`、`suspend debug`、`add wake up`、`remove wake up`；
- USB 线：`otg udc vbus`、`fsl-usb2-udc`、`g_file_storage`，以及 Android 下的 `android_usb`、`g_android`；
- 本项目自己打印的一切：`pw3-`。本项目的补丁和程序都以这个前缀打印（例如补丁 1046 的 `pw3-usb:`），以后新加的诊断不必再改清单。`pw3-boot-report` 例外，排在拒绝表（`DENY`）里先查掉；
- 存储：`mmc0`、`mmcblk`、`sdhci`、`emmc`、`EXT3-fs`、`EXT4-fs`；面板：`mxc_epdc`、`imx_epdc`；原厂电源事件：`KERNEL: I pmic:`；
- 内核出事：`Unable to handle kernel`、`Internal error`、`Kernel panic`、`Oops`、`BUG:`、`WARNING:`、`Backtrace:`、`watchdog`，以及它们下面说明"在哪、怎么到这儿"的转储（回溯帧 `[<`、寄存器行、`PC is at `、`LR is at ` 等）；内存：`Out of memory`、`page allocation failure`。

另外三条规则：

- **第二道闸**：允许的行里如果又出现 MAC 地址、12 位以上连续十六进制、或 `ssid`/`serial`/`command line`，整行丢掉。它拦的是没想到的那一行；在采到的日志里，没有一行走到它。
- **SELinux 拒绝单独处理**：只留本项目自己的域（`scontext=u:r:pw3_…`）；带 `path=` 的，路径必须在 `/dev`、`/sys`、`/proc`、`/system` 下；带 `name=` 的整行丢掉——那可能是一本书的文件名。开发期间有一次装完后启动被拒，原因正是一条 SELinux 拒绝，而它被清单筛掉了，交出来的目录里什么也没说。
- **有意不收的**：`mmc1`（Wi‑Fi 卡的 SDIO 总线，单是枚举就 1,476 行；镜像在 mmc0/mmcblk0）；`Code:`（指令字节，用户态程序崩溃时这一行印的是应用自己的字节）；`Process`（当时在跑什么，是使用者的事）。

实测（`userlog.c` 开头）：在设备上采到的 201 份内核日志（96,545 行）上，保留 10.2% 的行；每份 32 KB 筛后约 3.1 KB，一次点击三份合计约 9 KB。筛过的文件首行写 `pw3-kernel-log-filtered-v1 source=<来源>`，末行写 `pw3-kernel-log-filtered-v1 kept=N left_out=N`，读的人知道这是筛过的、筛掉了多少。

内存里的日志缓冲区不动：预检要拿休眠前后两份日志比对（`new_log_suffix`、`pm_log_has_error`），比对的若是筛过的日志，就看不见没被告知过的错误。过滤只发生在写文件那一刻。

## 安装画面

### 做法

- **怎么上屏**：原厂 `eips -g 图片 -x -y -w 波形` 能显示 PNG（[MobileRead wiki](https://wiki.mobileread.com/wiki/Eips)，多个项目在用）。
  - `eips` 本身已按固件核对哈希，行为固定。
  - 比自己写帧缓冲简单，不必处理原厂 3.0 内核的 EPDC 接口。
- **构建时**（`screens/render_screens.py`，构建机里装了 Ubuntu 的 `python3-pil` 9.0.1）：
  - 把每个画面的中英文排版成 8 位灰度位图，zstd 压缩后放进辅助程序。24 屏加数字字形，2026-10-31 这一版共约 588 KB（`screens-*/build-result.json` 里有当次的准确值）。
  - 字体用 AOSP 源码里的 Noto Sans CJK SC（OFL）和 Roboto（Apache-2.0），与系统界面一致。发行物里只有渲染出的位图，没有字体文件。
  - 文字全部集中在这一个文件里；下载大小等数字取自载荷清单。
- **设备上**（`install/screen.c`）：
  - 用位图、进度条和数字拼出画面，写成不压缩的 PNG（944×1193，约 1.1 MB，放在私有的 `/tmp` 目录），调用一次 `eips -g`。
  - 每次都画同一块区域，短画面会盖掉长画面留下的字。
- **画面**：检查、下载、核对、安装第 1 步和第 2 步、重装损坏的系统文件、准备启动、启动中、更新后第一次启动、E101–E403 共 13 种错误、没能启动，共 23 个。
  - 进度画面带进度条和百分比；E401 显示还差多少 MB。
  - 安装器入口里，辅助程序原有的英文文字提示都换成了对应画面。
  - 检查失败时显示"没能启动"画面并以 3 退出，入口脚本不再覆盖。
- **排版**：区域从 (64, 176) 开始，宽 944 px，避开原厂状态栏。
  - 字号：标题 52/40 px（约 28 sp），正文中文 38 px（20 sp）、英文 32 px（17 sp），都不小于界面规范（`docs/design/eink-ui.md`）第 8 条的 16 sp。
  - 黑字白底；进度条描边 2 px（规范第 3 条）。
  - 中文按字断行，句末标点不放行首，开引号不留行尾；英文单词和数字不拆开。
- **刷新**：
  - 进入安装器时 `eips -c` 清一次屏，会闪一下。这是从书库切到安装画面的那一下。
  - 之后每次更新只改变化的像素，用 GL16，不闪。
  - 同一画面要百分比变了、且距上次至少 3 秒才重画。

### 测试

`install/test_screen.py`：每个画面由 C 代码拼出，与构建时 Python 画的预览逐像素相同；PNG 经 Pillow 和 zlib 解码，CRC 和 Adler-32 都对。它已接进 `tools/run-tests.py`（构建机里有字体和 Pillow 时自动跑）。预览图在 `render_screens.py` 输出目录的 `preview/` 下。

### 尚未在真机上验证的

- 执行的波形是不是 GL16：`eips` 打印的是**请求**的波形，要开原厂内核的 `mxc_epdc_debug` 从内核日志核对。
- 原厂界面（状态栏时钟、书库扫描）会不会盖掉安装画面。

### 启动画面写明没能启动时怎么办

框架反复重启时，屏幕会一直闪，使用者无从判断也无从脱身。屏幕在闪的时候什么提示都显示不出去，唯一能被看到的时刻是启动之前，所以写在启动画面上（依据见 `docs/design/diagnostics.md`「启动失败时的出路」）：

- `BOOT`：启动时屏幕可能长时间不变，这本身不代表失败，不要强制重启；启动失败时，Kindle 通常会在几分钟内自己重启回原来的系统，书不会丢；没有自己回去，就按住电源键不放，直到屏幕变化（最多约 40 秒），同样回到原来的系统。回到了书库就再点一次：如果是系统文件坏了，这一次会自己查出来并重装，不需要电脑。书和应用数据都在另一个文件里，不会丢。
- `BOOT_UPGRADE`：先说已安装的应用要为新系统重新编译、每个应用大约三到五分钟，再说启动失败时 Kindle 通常会在几分钟内自己重启回原来的系统。

两屏都不写启动要多久，也不按症状分类（屏幕不动既可能是正常启动，也可能是入口拒绝后那两分钟的等待）。理由在 `docs/design/diagnostics.md`。

### 区域高度按每个画面真正要画的算

画面区域是固定的一块，设备每次都整块擦掉重画；它的高度取所有画面里最高的那一屏，放不进状态栏以下、屏幕以内，`render_screens.py` 就停止构建。

高度按每个画面自己要画的东西算：有进度条才留进度条和百分比的位置（165 px），没有就只看 `pw3_screen_number`（`screen.c` 的 `screen_render`）。曾经给**每个**画面都留出进度条和数字的位置再取最高，结果在最长的 `BOOT`（既没有进度条也没有数字）下面留出一块谁也用不到的空地，然后报"放不下"（1362 px，屏幕只给得出 1272 px），而画面本身是放得下的。现在区域是 944×1193。

除了做发行版，没有别的东西会去渲染这些画面，这个错误曾经三天没人发现。所以渲染和 `test_screen.py` 都接进了 `tools/run-tests.py`（构建机里有字体和 Pillow 时自动跑，没有就按惯例列为跳过）。

### `BOOT` 这一屏有两个画它的程序

交接之后那一侧也要画它，因为新内核的显示驱动初始化时会清掉面板、再把自己那块刚分配的缓冲区刷出去，安装器用 eips 画的东西活不到那时候。所以 `BOOT` 的文案提到了 `render_screens.py` 的模块级常量（`BOOT_ZH`、`BOOT_BODY`、`STUCK_*`、`AGAIN_*`），由 `boot/handoff-init/make-start-picture.py` 用同一套排版、同一份字体再渲一份，行程编码成 `boot/handoff-init/start-picture.h`，交接程序加载完驱动就画上去。

交接程序只画 `BOOT` 这一屏。更新后第一次启动时，交接之前屏幕上是 `BOOT_UPGRADE`，交接之后换成普通的 `BOOT`，一直到 Android 第一帧。

**改这一屏的文案时要知道**：改常量就够了，两边都跟着变；但 `start-picture.h` 是提交进仓库的生成物，要重跑一次 `--write`。`tools/run-tests.py` 的 `handoff-start-picture` 一项就是守这个的——文案改了而头文件没重生成，它会失败。

## 更新后应用重新编译

**问题**：每个新版本的构建指纹都不同（含构建时间），Android 每次都按"系统升级"处理；启动镜像一变，`/data` 里应用的机器码随之失效。

AOSP 8.1 的做法（`PackageManagerService.updatePackagesIfNeeded`，已读源码核实）有三个问题：

| 问题 | 后果 |
|---|---|
| 用 `pm.dexopt.boot` 重编，默认 `verify`，即不生成机器码 | 应用下次启动没有机器码。早期在本机实测，微信读书这样启动超过 2 分钟，还会弹"无响应"；后来复测约 41 秒、不再弹窗（`device/amazon/pw3/pw3.mk` 注释） |
| 只在第一次看到新指纹的那次开机重编 | 中途强制重启后，下次开机已不算升级，应用一直没有机器码 |
| 跳过"上次使用前一周内没用过"的应用 | 久未打开的应用下次打开很慢 |

**做法**：`frameworks/base` 的三个补丁，加上 installd 那一半（`patches/aosp-frameworks-native/`）。改的是 `services.jar` 和 installd，都不在启动镜像里，不会让已有应用失效。

- `frameworks/base 0026`：`/data` 里的应用（使用者装的，或在 `/data` 更新过的系统应用）每次开机都检查，不管最近是否用过。
  - 机器码仍匹配的立即跳过，平常开机只多几次文件头检查；
  - 某次开机在编译中途被打断，下一次开机会接着完成；
  - 系统应用仍用 `pm.dexopt.boot`：它们在 `/system` 里的机器码就是按新启动镜像编的，会被直接跳过。
- `frameworks/base 0047`：这些应用按自己的使用画像编译，过滤器用 `pm.dexopt.ab-ota`（`pw3.mk` 设为 `speed-profile`）。补丁说明里的实测：微信读书带八天阅读的画像，按画像编 181 s、机器码 75 MB，全量 `speed` 编 1410 s、180 MB，而冷启动按画像编的反而更快。
- `frameworks/base 0051`（配 `frameworks/native 0008`）：没有画像的应用改为 `quicken`。按一份不存在的画像编译，dex 照样被快速化，结果与 `quicken` 相同，耗时却是两倍半（同一台设备上 147 s 对 62 s）。
- 编译发生在 system_server 启动看门狗之前（`SystemServer.java` 第 955 行 vs 第 1759 行）。dex2oat 带 `--no-watch-dog`（installd 也读 `dalvik.vm.dex2oat-flags`，见 `device/amazon/pw3/system.prop`），不会因超时被中止。

**代价**：更新后第一次开机要等编译完。一个大应用约一到三分钟：微信读书（127 MB）有使用画像时实测 159–181 秒，没有画像时 60–93 秒（补丁 0047、0051 的说明，以及 `docs/install.md`「升级」）。

- 安装器知道这是一次"保留数据的更新**且换了启动镜像**"（`inst_result.upgraded`），启动前显示专门的画面（`BOOT_UPGRADE`）："每个应用大约三到五分钟，装得多就更久，期间屏幕不变，请接上充电器，不要强制重启"。启动镜像没换的升级不显示它（见"只在换了启动镜像时提示重编译"）。交接之后屏幕换成普通的 `BOOT`（见"安装画面"）。
- 启动路径上如果要加任何超时（例如"启动太久就回原厂"），要把这段编译时间算进去。

**测试**：安装器测试检查了 `upgraded` 标志（首次安装为 0，换了启动镜像的升级为 1，没换的为 0）；画面逐像素一致。

**真机**：2026-10-29 在设备上装过一次换了启动镜像的升级（45 个启动文件全变）：第一次开机进到了桌面，开机后约 3 分钟，微信读书的 `base.vdex` 重写完，`dumpsys package` 报 `status=kOatUpToDate`。但存机器码的 `base.odex` 没有重写，仍是之前后台编出来的那份。启动镜像换了它为什么仍被判定有效，还没查清，所以这次不能当成"一次完整重编只要 3 分钟"的证据。

## 上机检查脚本 `Android-Installer-Check.sh`（`probe/build_check.py` 构建）

把安装流程和安装画面依赖原厂系统的几项一次量完，不动任何已有文件：只写自己的文件夹 `/mnt/us/android-check-<时间>/`，结束时删掉临时文件，只留 `report.txt`。不记录设备标识、网络名或地址。约 5 分钟，需要 64 MiB 空闲。

| 检查 | 怎么做 |
|---|---|
| 安装画面 | `eips -c` 清屏一次，再用安装器同样的 `eips -g … -w gl16` 依次显示两个由 `screen.c` 画出的画面（下载 37%、E401），各停 8 秒；记录返回码，画面要有人看一眼 |
| 网络 | 只用内置证书库，HEAD 请求百度、Cloudflare（对照）、`api.github.com`、`github.com`，记录握手耗时；区分"设备 TLS 有问题"和"这个网络连不上 GitHub" |
| 下载与续传 | 用安装器的同一组 `curl` 参数下载 EinkBro 4 MB 发行文件并核对 SHA256；截到 1 MB 后续传，再核对 |
| 原厂接口 | `lipc` 读电量、充电、Wi‑Fi 状态；屏保保持后恢复原值 |
| 解包 | `pw3-unpack` 展开 64 MiB 测试镜像，记录耗时和前后内存，然后删除 |

- 构建：`probe/build_check.py`（构建机），所含的每个文件在设备上先核对 SHA256。有一个文件损坏就立即停止，什么都不改，屏幕提示重新拷贝。
- 构建机演练（2026-10-15）：
  - 换上桩程序（`eips`、`lipc`）、用户区换成临时目录、`curl` 用真实网络，整套流程跑通；
  - 4 个站点校验通过，下载和续传（HTTP 206）SHA256 都对；
  - 64 MiB 解包在 QEMU 下 0.85 秒，最后只留 `report.txt`。
  - 演练还暴露了一个缺陷：文件没解出来时，空文件被当成脚本执行，返回 0，看起来像成功。所以脚本在文件没解出来时一开始就停。
  - 构建机的 curl 是新版 OpenSSL；原厂是 1.0.2q，所以网络这几项以上机结果为准。

### 上机结果（2026-10-19，PW3，固件 5.16.2.1.1）

全部通过：

| 问题 | 结果 |
|---|---|
| 原厂 `eips -g` 能否显示 8 位灰度 PNG | **能**。两张画面 `rc=0`，130 ms 和 170 ms，输出 `update_mode=PARTIAL, wave_mode=5`（即请求的 GL16，局部刷新）。安装画面用 `eips -g` 的做法成立 |
| 原厂 `curl`（OpenSSL 1.0.2q）配自带证书能否下载 GitHub | **能**。百度、Cloudflare、`api.github.com`、`github.com` 四站 HEAD 全部 200、`ssl_verify_result=0`；github.com 握手 0.48 s |
| 下载与续传 | 4.03 MB 用 2.98 s（**1.35 MB/s**），SHA256 对；截到 1 MB 后续传返回 **HTTP 206**，续完 SHA256 也对。**10-15 那次失败是网络，不是设备** |
| `lipc` 读数与屏保 | 电量 100、未充电、Wi‑Fi `CONNECTED` 都读到；`preventScreenSaver` 置 1 成功、结束恢复为 0 |
| `pw3-unpack` 速度与内存 | 64 MiB 用 **27.18 s**（2.47 MB/s，写 FAT 为主）；`MemFree` 91 MB → 74 MB，8 MiB 窗口够用 |
| 空闲空间 | 用户区 3.04 GiB 中空闲 **611 MiB**（当时设备上已有的 system.img + data.img 占着 2.3 GB），不够走一次完整安装 |

按这些速度推算首次安装：下载约 191 MB 约 2.4 分钟 + 展开系统镜像约 4～5 分钟 + 生成 1.88 GB 数据镜像约 13 分钟，合计约 20 分钟。后来用离线包实测首次安装约 18 分钟（不含下载，`docs/install.md`）。

**尚未在真机上验证**：`wave_mode=5` 是 `eips` 打印的**请求**波形，不是内核日志确认的**执行**波形，而请求的波形不一定就是执行的波形。要开原厂内核的 `mxc_epdc_debug` 再核。画面确实显示出来了，所以用 `eips` 的前提成立；没确认的是"更新那一下闪不闪"。

## 探针要量的未知项

探针 `probe/Android-Probe.sh` 在原厂系统上量出安装器能依赖什么：

| 问题 | 为什么重要 | 探针怎么量 |
|---|---|---|
| 原厂 `curl` 能否用 TLS 下载 GitHub 的发行文件；证书库是否过期 | 决定能不能直接用原厂工具下载，还是要自带 HTTPS 客户端和证书 | 下载 EinkBro 4 MB 发行文件，核对 SHA256；失败时再试一次不校验证书，区分原因 |
| 下载速度、是否支持断点续传（Range） | 估计安装时长，决定续传方案 | 计时；请求一段 Range |
| 安装期间能否阻止原厂进入屏保和休眠 | 否则 Wi‑Fi 会断 | 设置 `preventScreenSaver` 并读回，结束后恢复 |
| 用户区写入和读取速度 | 展开 2 GB 数据镜像要多久 | 写 64 MiB、清缓存后读回 |
| 原厂 `eips` 能否显示图片 | 中文提示用图片还是自己写屏 | 读 `eips -h` |
| 剩余空间、电量、固件版本、内存 | 安装前检查的依据 | 直接读 |

探针不记录序列号、MAC、网络名或地址。它只在 `/mnt/us/android-probe-<时间>/` 下写文件，测试完删除自己的临时文件。

## 探针实测（2026-10-15，PW3，固件 5.16.2.1.1）

| 项目 | 结果 | 对安装器的含义 |
|---|---|---|
| 原厂 `curl` | 7.86.0，OpenSSL 1.0.2q，`/etc/ssl/certs` 下 4 个文件 | 版本支持 TLS 1.2 和 SNI，够连 GitHub |
